# 修复报告 v1.11.0（2026-11-07）

> **一句话**：2026-11-02～11-07 移动账号连续 5 天不可用的根因是**中国移动
> wx.10086.cn 整站系统升级维护**，不是账号/代理/d.sid 问题；本次修复把"维护"
> 从"故障"里分离出来，并修掉三个被掩盖的判定缺陷。

完整根因与证据链见 [线上故障根因-移动网厅维护-2026-11-07.md](线上故障根因-移动网厅维护-2026-11-07.md)。

## 一、线上现象

| 时间 | 事件 |
|---|---|
| 11-02 02:50～03:10 | 移动连续 4 次成功（16 字段） |
| 11-02 03:12 | v1.10.1 部署完成 |
| 11-02 03:41 | 移动首次失败（network，0.82s），此后每 30 分钟一次，间隔精确 |
| 11-05 10:53 | HA 重启 → session_state 传感器最后一次写入，停在 `healthy`/`fail_streak=1` |
| 11-07 00:44 | 最后一次失败事件（累计 380+ 次） |

事件日志全量分类（785 条）：

```
mobile    network           278   ← 维护期误判
mobile    auth_expired       15   ← 维护期误判（危害更大，见下）
unicom    auth_expired       79   ← 真实失效（用户未处理）
mobile    internal           11

```

## 二、根因（实测闭环）

**中国移动 wx.10086.cn 整站返回「升级公告」HTML 页**：

| 端点 | HTTP | 响应体 title |
|---|---|---|
| `/website/spa/main/newHome` | 500 | 升级公告 |
| `/website/serviceMargin/getMainPlan` | 404 | 升级公告 |
| `/website/fareBalance` | 404 | 升级公告 |
| `/website/uniApi/getNewMarginInfo` | 500 | 升级公告 |
| `/website/score/news` | 404 | 升级公告 |
| `/website/uniApi/getMarginQueryInfo` | 500 | 升级公告 |

排除项（均有实测支撑）：

| 假设 | 排除依据 |
|---|---|
| 代理链路故障 | `api.ipify.org` 经同代理 → 200；出口 IP 三次连测均为 212.135.214.8（未漂移） |
| 账号/会话失效 | 公告页与账号无关；不带 cookie 时 newHome 返回 200「登录」页 |
| d.sid 过期 | 带 cookie 请求返回的是公告页而非登录页；不重签一样 |
| 端点下线 | 404 响应体是同一张公告页，不是 404 页面 |

> **重要陷阱**：不带 Cookie 探测会误判——服务端把请求导向登录页并返回
> `HTTP 200 登录`，看起来像"已恢复"。只有带 Cookie 才是有效探测。

## 三、修复的 4 个缺陷

### 缺陷 1：公告页被误判为 protocol_drift / network

**位置**：`api/mobile.py::_wx_query`、`api/base.py`

- 修复前：404/410 → `ParseAnomalyError`（protocol_drift = 端点下线）；
  其他非 200 → `CarrierError("网络错误")`（network）
- 修复后：新增 `CarrierMaintenanceError` 与 `is_maintenance_notice(body)`，
  **判据是响应体内容而非状态码**（同一个 404/500 既可能是公告也可能是真故障）

公告页特征词分**强/弱两档**：

- 强特征（单独即可判定）：`升级公告` `系统升级` `系统优化升级` `升级期间`
  `维护升级` `暂无法提供服务` `正在玩命调试`
- 弱特征（需搭配上下文）：`稍后再试` `敬请谅解` `请稍后` `系统维护`
  + 上下文词 `系统优化` `升级公告` `正在升级` `优化升级` `暂停` `不可用`
  `暂时无法` `稍后开放`

> **为什么分两档**：`稍后再试` / `敬请谅解` / `系统维护` 是极通用的礼貌语与
> 常见词，在任何运营商的错误页、限流页、用户协议页上都可能出现。若把它们当
> 强特征，一次**真实故障会被永久误判成"维护中"**——用户看到的只是"运营商
> 维护中"，永远不会去查真实原因，比原缺陷更难排查。

### 缺陷 2：v1.10.1 自愈重试分支从未执行

**位置**：`api/mobile.py::_wx_fetch`

- 修复前条件：`len(failures) >= 4 and not anomalies`
- 真实故障形态：failures 与 anomalies 会被**分类切分**（实测 failures=2、
  anomalies=3）→ 两个条件都不成立 → **5 天 380+ 次失败里重试一次都没跑过**
- 修复后：按"失败端点 / 本轮尝试端点"的比例判定
  （`all_down = attempted > 0 and total_failed >= attempted`）
- **维护态不触发重试**：凭据是好的，重签 d.sid 毫无意义，只会加倍风控暴露

### 缺陷 3：session_state 传感器停更

**位置**：`coordinator.py::_notify_failure_state`

**HA 2026.10.4 源码依据**（`helpers/update_coordinator.py`）：

```python
if not self.last_update_success and not previous_update_success:
    return          # 连续失败（本次失败 + 上次也失败）→ 直接返回，不通知
if (self.always_update or ...):
    self.async_update_listeners()
```

即 HA 只在**状态跃迁**时通知 listener：首次失败（成功→失败）会通知一次，
此后的**连续失败全部被早退吞掉**——`always_update=True` 也救不了，因为早退
发生在 `always_update` 判断之前。

> 这解释了线上 `fail_streak=1` 的确切来源：HA 于 11-05 10:53 重启后首轮失败
> 写入 1（跃迁通知），此后 74 次连续失败全被吞掉 → 传感器永远停在 1，
> 而协调器实际已累计 75 次失败。

**修复**：失败路径显式调用 `async_update_listeners()`。

**顺序要求（已在代码注释中标注）**：必须**先置 `last_update_success = False`
再通知**。否则 `CarrierSensor.available`（判据
`not last_update_success and not self._data`）会用旧的成功状态算出
`available=True`，把本该 unavailable 的实体写成 unknown —— 比"停更"更糟。

### 缺陷 4：诊断包 recent_events 未按账号过滤

**位置**：`diagnostics.py::_summarize_events`

多账号共用同一个事件日志文件，不过滤时各账号下载到的诊断包 `recent_events`
**逐条相同**（实测移动与联通完全一致），排障时会指向错误的账号。

修复：`_summarize_events(path, carrier=None)` 增加 carrier 过滤，调用处传入
`entry.data.get("carrier")`。保持「不输出 phone」的既有约束（威胁模型 R2）。

## 四、连带修复

| 项 | 说明 |
|---|---|
| 熔断兜底失效 | `CIRCUIT_COOLDOWN` 原为硬编码 900s < 轮询间隔 1800s，且 `_last_fail_at` 每轮刷新 → 条件恒假 → 熔断分支（唯一会 return 而非 raise、从而能通知 listener 的分支）**永远进不去**。改为动态 `_circuit_cooldown()` = max(3600, 轮询间隔×2) |
| network 类无退避 | `_apply_adaptive_interval` 只在认证失败时调用 → 维护期 38 小时按 30 分钟硬打了 380+ 次必然失败的请求。新增 `_apply_network_backoff()`（2 倍起，封顶 6 小时） |
| 维护态的有害副作用 | 维护期**不**累加熔断计数、**不**推高认证计数、**不**弹「请重新登录」、**不**自动发短信、**不**发 reauth 卡片、**不**触发自愈重试 |
| 新增 `maintenance` 状态 | `session_state` 返回值从四态扩展为五态（`healthy` / `degraded` / `needs_human` / `circuit_open` / `maintenance`） |
| 新增失败分类 | `classify_exception` 增加 `maintenance`（第六类），判定顺序排在 `CarrierAuthError` 之前 |

## 六、遗留问题

1. **端点路径随运营商升级变更**：`serviceMargin/getMainPlan` 在维护期间返回
   404。维护结束后它是否仍存在需届时复核；若运营商改了路径，集成恢复后仍拿
   不到数据。建议后续加「连续 N 轮全公告 → 自动降级为维护态并通知用户」
   的行为（P1）。
2. **联通 cookie 需人工重登**：服务端会话过期，集成无 openid/短信自助通道。
   属既有待办，本次未动。
3. **漂移金丝雀覆盖不到本次故障**：`tests/canary_endpoints.py` 探测的是
   `login.10086.cn`（不同子域）+ 联通/电信/广电，无凭据；且无凭据探测在整站
   维护期会误判为"已恢复"。**故障期间金丝雀全绿属预期行为**。本次**未改**
   canary（不应改），未来若要覆盖需另立项目（带凭据 canary 或给 HTML 指纹
   加入正文文本归一）。
4. **HA recorder DB 4.5 GB**：膨胀主因是 `miwifi_router` 集成（每设备 10 万
   条 states，共 670 万行），与本集成无关；`purge_keep_days: 5` 已生效但
   SQLite 删除行不返还空间，需 VACUUM 或压缩备份。属独立支线。
