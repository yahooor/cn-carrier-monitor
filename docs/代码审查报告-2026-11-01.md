## 一、项目结构与运行流程

### 1.1 目录结构

```
custom_components/cn_carrier_monitor/
├── __init__.py       # 服务注册（refresh / inject_token）、webhook 注册、前端图标、条目装载
├── const.py          # 域名/运营商/端点/常量
├── coordinator.py    # 每账号 DataUpdateCoordinator：轮询、熔断、降级、凭证回写、短信重登
├── config_flow.py    # 分运营商分步配置流 + reauth + options
├── sensor.py         # 动态实体（按数据字段决定建哪些实体）
├── button.py         # 手动刷新按钮
├── diagnostics.py    # 脱敏诊断
├── event_log.py      # JSONL 事件日志（四分类）
├── net.py            # 连接器：IPv4 + 公共 DNS + legacy TLS
├── webhook.py        # 短信验证码回传 → 自动重登
└── api/
    ├── base.py       # CarrierClient 基类、归一化模型、parse_safe
    ├── crypto.py     # AES/RSA/JSONP/cURL 解析
    ├── telecom.py    # 电信：v1 密码族 + v2 短信族 + 滑块自动过
    ├── unicom.py     # 联通：App 密码 / 短信 / 网页 Cookie / 小程序 openid
    ├── mobile.py     # 移动：网厅登录 + wx 查询 + 12.5 原生协议
    └── broadnet.py   # 广电：cURL 会话重放
```

### 1.2 四条主流程

**① 配置流（config_flow）**
`user`（选运营商）→ `*_mode`（选登录方式）→ 分运营商步骤（发码 / 输码 / 密码 / Cookie / cURL 导入）→ `_persist()` 写条目。每个条目 = 一个号码，`unique_id = f"{carrier}_{phone}"`。

**② 轮询流（coordinator）**
`async_setup_entry` → 创建 coordinator（独立 `ClientSession`）→ `async_config_entry_first_refresh()` → 转发 `sensor`/`button` 平台 → 按 `update_interval` 调 `_async_update_data()` → `client.async_fetch()` → 归一化 dict → 实体读取。

失败分层：`CarrierAuthError` → 有旧数据则降级返回（打 `login_expired` 标记），无数据则 `ConfigEntryAuthFailed`（触发 reauth）；`CarrierError`/其他 → `UpdateFailed`（连续 5 次熔断 15 分钟）。

**③ 登录 / 重认证流**
- 手动：配置流内直接调各 client 的 `async_login*`，成功后把 token/cookies 写进条目。
- 自动：查询命中 `CarrierAuthError` → 若为短信模式 → 后台发码（限频）→ 用户转发器 POST webhook → `_relogin()` 提交验证码 → 写回条目 → reload。
- 官方：`ConfigEntryAuthFailed` → HA 启动 reauth flow → `async_step_reauth` 按原 `auth_mode` 回到对应步骤。

**④ 会话保持流**
- 电信 v1：token 长效，查询失败自动用服务密码重登。
- 联通：每次拉取前 `onLine.htm` 续期 `token_online`。
- 移动：`refreshSession` 保活 + `uuid → d.sid` 自愈（GET 首页触发重签，回收 Set-Cookie）。
- 广电：无续期，靠人工重新导入。
- 成功后 `_async_persist_credentials()` 把轮换后的凭证写回条目。

## 二、问题清单（按严重程度）

> 编号即后文修复说明与测试用例的对应关系。P0 = 功能不可用/安全失守；P1 = 长期运行不稳定；P2 = 正确性/可维护性缺陷。

### P0（6 项）

| 编号 | 问题 | 根因 | 用户可见现象 |
|---|---|---|---|
| **P0-1** | **HA 重启后所有传感器消失** | `sensor._sync()` 用实体注册表 `async_get_entity_id()` 判断"已存在则跳过"，但注册表里的条目恰恰是上一次运行创建的——重启后每个 unique_id 都能查到，于是**一个实体都不会被创建** | 第一次配置正常，重启 HA 后实体全部不可用，只有删条目重加才恢复 |
| **P0-2** | 修改轮询间隔 / webhook 密钥不生效 | `async_setup_entry` 没有 `entry.add_update_listener`，options 变更后 coordinator 仍用旧值，只有重启 HA 才生效 | 把间隔从 60 分钟改成 30 分钟，实际仍按 60 分钟轮询（风控预算失效） |
| **P0-3** | 重新认证完成后条目不重载 | `_persist()` 用 `async_update_entry()` + `async_abort("reauth_successful")`，只改数据不重载 | 输完验证码提示成功，但实体仍然不可用，必须重启 HA |
| **P0-4** | 首次认证失败不触发 reauth | `async_setup_entry` 用 `except Exception` 包住 `async_config_entry_first_refresh()`，把 `ConfigEntryAuthFailed` 一起吞了 | 添加集成时若 token 已失效，实体以不可用状态创建，永远不弹"重新认证" |
| **P0-5** | `cn_carrier_monitor.refresh` 服务报错 | 短信发码状态存在 `hass.data[DOMAIN]["sms_state"]`，而该字典本来以 `entry_id` 为键存 coordinator；服务遍历时对 dict 调 `async_request_refresh()` | 只要用过一次电信/联通短信登录，刷新服务就抛 `AttributeError` |
| **P0-6** | **出站 TLS 全局关闭证书校验** | `net.py` 用 `verify_mode=CERT_NONE` + `check_hostname=False` 建上下文，所有运营商的密码/token/Cookie 都在可被中间人读取的通道上传输；文档里却写着"TLS 校验默认开启" | 无感，但同网段/上游链路上的攻击者可拿到服务密码与会话 |

`custom_components/cn_carrier_monitor/sensor.py`

```python

    created.add(k); continue
```

同时 `_desired_keys()` 末尾加 `list(dict.fromkeys(keys))` 去重，并删掉重复的 `location` / `plan_price` 两段。**先修根因（重复键）再拆创可贴（注册表守卫）**，否则重复键会重新制造 duplicate unique_id 报错。

### P0-2 选项生效

`__init__.py` 注册监听器，coordinator 侧存选项快照：

```python
coordinator.options_snapshot = dict(entry.options)
entry.async_on_unload(entry.add_update_listener(_async_entry_updated))

async def _async_entry_updated(hass, entry):
    coordinator = _coordinators(hass).get(entry.entry_id)
    if coordinator is None or dict(entry.options) == coordinator.options_snapshot:
        return          # 凭证滑动续期只改 data，不重载
    coordinator.options_snapshot = dict(entry.options)
    await hass.config_entries.async_reload(entry.entry_id)
```

**关键**：不能用无脑 `async_reload` 的监听器——`_async_persist_credentials()` 每次轮询都会 `async_update_entry`，无脑重载会变成"重载 → 刷新 → 写凭证 → 重载"的死循环。快照比较是这里的必要条件。

### P0-4 首次失败走标准机制

```python
try:
    await coordinator.async_config_entry_first_refresh()
except Exception:
    await coordinator.async_shutdown()   # 必须先关会话，否则每次重试漏一个 ClientSession
    raise                                # AuthFailed → reauth；UpdateFailed → NotReady 退避重试
```

行为变化：首次拉取失败时不再创建"不可用实体"，而是由 HA 走 reauth / 退避重试。这是官方推荐路径（`developers.home-assistant.io/docs/integration_setup_failures`），也是"登录过期能自动弹重新认证"的前提。

### P0-6 TLS 证书校验

`net.py` 重写：

```python
ctx.verify_mode = ssl.CERT_NONE if insecure else ssl.CERT_REQUIRED
ctx.check_hostname = not insecure
ctx.options |= getattr(ssl, "OP_LEGACY_SERVER_CONNECT", 0x4)
ctx.set_ciphers("DEFAULT:@SECLEVEL=1")     # 旧套件照旧放行
```

- 原来的 `CERT_NONE` 是**误诊**：运营商网关的问题是 1024 位 DH / SHA1 等旧套件被 SECLEVEL=2 拒绝，`SECLEVEL=1` + legacy-connect 即可，不需要放弃校验。
- 保留逃生阀：`CN_CARRIER_INSECURE_TLS=1` 才降级，且每次启动打 WARNING。
- 新增 `warm_ssl_context()`，由 `async_setup` 在 executor 预热 `load_default_certs()`，避免 HA 的 blocking-call 告警。

> 回滚方式：若某运营商确因证书问题连不上，设 `CN_CARRIER_INSECURE_TLS=1` 重启即可恢复旧行为。

### P1-13 凭证回写节流 + 退化保护

```python
CREDENTIAL_PERSIST_INTERVAL = 600.0          # 10 分钟最多写一次
if self._looks_like_regression(old, value):  # 空值 / Cookie 名骤减 → 拒绝写回
    continue
```

`_looks_like_regression()`：新值为空 → 拒绝；旧值是 Cookie 串（含 `;` 与 `=`）而新值 Cookie 名数量少于旧值一半 → 拒绝。这是对"自动刷新凭据把有效会话覆盖成空"这类事故的硬保险。

### P1-17 发码指数退避

## 五、登录方案对比与推荐

### 5.1 现状为什么"不稳定"

四条独立原因叠加，不是单一 bug：

1. **协议层错配**：电信 v2 短信 token 是**分钟级一次性**凭据（项目自己的《会话生命周期语义表》§2 实证 X201），拿它做 60 分钟轮询必然每次都失败——这不是代码 bug，是"用一次性钥匙去开长时段门"。
2. **会话层互斥**：移动服务端是**单设备最新会话互斥**。社区实测（Pocket-Carrier v3.7.0）在手机 App 关闭前提下 10 分钟一刷、连续 190 分钟 20 轮全绿；一旦手机打开 App，App 会毫秒级申请新票据并**强制踢掉旧凭据**。所以"移动 Cookie 模式不稳"的主因在用户侧行为，不在代码。
3. **工程层缺陷**：deviceId 跨步骤丢失、瞬时错误被判成掉线、发码 5 分钟冷却、reauth 不重载——这些是本次修掉的部分。
4. **状态层缺失**：所有失败走同一条路（发码 / 降级 / reauth 混杂），没有"这是可恢复的 token 过期"与"这是账号被锁，只能人工"的区分。

### 5.2 四类方案对比

| 维度 | **A 服务密码 / App 协议登录** | **B 短信验证码（含自动滑块）** | **C 浏览器会话导入（Cookie / cURL）** | **D App 抓包凭据导入（12.5）** |
|---|---|---|---|---|
| 代表实现 | 电信 v1 `userLoginNormal`；联通 `login.htm`；移动 `login.htm` pwdType=01 | 电信 v2 `appgologinsz` + 滑块；联通 `radomLogin` + H5 resultToken；移动 `sendRandomCode` | 广电 cURL 重放；移动 `inject_token` 灌 uuid | Pocket-Carrier 移动 `getFamilyCube` cURL |
| 登录流程 | 一次 POST 换 token，全自动 | 发码 → 过滑块 → 输码 → 换 token，需人工/转发器介入 | 人在浏览器登录，导出会话 | 人在 App 抓包，导入 cURL |
| 验证码处理 | 不需要 | 需自动过滑块（本项目 PIL 缺口定位，误差 ≤4px）或人工转发 | 不需要（人已完成） | 不需要 |
| 会话保持 | **最强**：token 长效 + 失效可用密码静默重登 | 弱：电信 token 分钟级；联通需重过滑块 | 中：移动 uuid 72h + d.sid 30min 自愈；广电约 3 天 | **强**：实测 3h10m+，手机不碰 App 可数周 |
| 稳定性 | 高（有密码即可无人值守） | 低（受短信频次/风控/滑块成功率三重约束） | 中（受人工周期约束） | 高（但需备用机） |
| 主要代价 | 需要服务密码；可能触发设备信任（3006） | 短信成本 + 风控 + 电信 token 短效 | 人工周期（小时~天） | 需抓包工具 + 备用机/模拟器 |
| 适用场景 | **默认首选**（有服务密码的账号） | 无密码账号的**一次性引导** | 广电（唯一可行）、被风控锁死密码登录的账号 | 移动长期监控 |

**结论**：不存在"一种登录方式通吃四家"。稳定性的来源不是更强的逆向，而是**把登录做成状态机、按运营商选对通道**。

### 5.3 推荐方案：分层会话状态机（SessionKeeper）

**核心思想**：登录从"每次查询的副产物"变成"独立状态机"，查询只消费状态、不负责登录。

```
             ┌──────────── 成功 ────────────┐
             ▼                              │
        ┌─────────┐   AUTH_SOFT   ┌──────────────┐
        │ HEALTHY │──────────────▶│ REFRESHING   │ 单飞锁 + 指数退避
        └─────────┘◀──── 成功 ─────└──────────────┘
             │                            │ 重登失败 N 次
             │ RATE_LIMIT / NETWORK       ▼
             ▼                     ┌──────────────┐
        ┌──────────┐               │ NEEDS_HUMAN  │──▶ HA 原生 reauth
        │ DEGRADED │               └──────────────┘
        └──────────┘   （保留旧数据，实体可用）
```

**错误分类器**（新增 `api/errors.py`，各 client 统一调用）：

| 分类 | 判据 | 处置 |
|---|---|---|
| `AUTH_HARD` | 密码错、账号锁定（电信 3008/3009、移动 8009/8012/8002、联通 4102/4103）、`unicom_forced_sms` | → `NEEDS_HUMAN`，`ConfigEntryAuthFailed`，停止自动重试 |
| `AUTH_SOFT` | token 过期（电信 1001/2001/X201/X110、移动 410000/400001、联通 999998/999999） | → `REFRESHING`，自动重登，30min→6h 退避 |
| `RATE_LIMIT` | 3007/3012、ECS1164、"频繁"、"验证码" | → `DEGRADED`，**不发码**，`UpdateFailed(retry_after=...)` |
| `NETWORK` / `PROTOCOL` | 连接/超时；HTTP 200 但结构漂移 | → `DEGRADED`，重试，**不动凭证** |

**分运营商默认策略**

| 运营商 | 默认 | 兜底 | 明确不推荐 |
|---|---|---|---|
| 电信 | 服务密码（v1 长效 token + 自动重登） | 短信（仅首次引导，或配合转发器做"按需刷新"） | 用短信 token 做定时间隔轮询 |
| 联通 | 服务密码（`onLine` 续期 + 失效重登） | 短信（需 H5 `resultToken`）；mall Cookie | 高频 mall Cookie（3-5 小时过期） |
| 移动 | **抓包凭据 / Cookie + 备用机**，间隔 ≥10 分钟 | 服务密码 | 主力机开着 App 同时用 Cookie 模式 |
| 广电 | cURL 会话导入 | — | 任何服务端登录尝试（WAF） |

**必须遵守的运行约束**（比代码更能决定稳定性）：

1. **移动账号用备用机/模拟器抓包**，抓完把主力机 App 划掉；否则顶号必掉。
2. 轮询间隔不低于文档预算（电信 30 / 联通 10-30 / 移动 30 / 广电 60 分钟），本次已加随机抖动错峰。
3. 一个账号只在一个 HA 实例里轮询（多实例 = 互相顶号）。

### 5.4 落地步骤

**阶段 1｜本次已完成（可直接发布 v1.5.0）**

2. 新建 `session.py`：
   ```python
   class SessionKeeper:
       state: Literal["healthy", "refreshing", "degraded", "needs_human"]
       async def ensure(self) -> None:      # 单飞 + 退避 + 自动重登
       def on_error(self, err: CarrierError) -> None:   # 状态迁移
   ```
   coordinator 只调 `await keeper.ensure()` 再 `client.async_fetch()`。
3. `UpdateFailed(retry_after=...)` 用于 `RATE_LIMIT`（HA 2024.6+ 支持，setup 首次刷新会转成 `ConfigEntryNotReady(retry_after)`）。

3. 诊断包展示 `session_state` / `credential_age` / `native_available`，让用户一眼看出"是掉线还是被顶号"。
