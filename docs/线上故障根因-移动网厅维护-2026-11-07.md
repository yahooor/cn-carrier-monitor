# 线上故障根因分析：中国移动网厅系统升级（2026-11-07）

> 结论先行：**不是账号问题，不是代理问题，不是 d.sid 问题，是中国移动 wx.10086.cn 整站处于系统升级维护状态。**
> v1.10.1 的「代理出口切换自愈」方案在原理上就修不了这个问题。

### 4. 关键陷阱：不带 cookie 探测会误判


## 三、由此暴露的 4 个代码缺陷

### 缺陷 1：公告页被误判为 protocol_drift / network

`api/mobile.py::_wx_query`：
- 404/410 → `ParseAnomalyError`（归 protocol_drift = 端点下线/迁移）
- 其他非 200（500）→ `CarrierError("网络错误: ...")`（归 network）

两者都错。维护是**暂时性**的：
- 归 protocol_drift 会污染漂移率统计，并让「协议漂移」看起来需要人改代码
- 归 network 会让用户以为网络坏了，且触发无意义的重试

### 缺陷 2：v1.10.1 的自愈重试分支从未执行

条件：`len(failures) >= 4 and not anomalies`

实测：failures=2（两个 uniApi 端点 500）、anomalies=3（三个端点 404）。
两个条件都不成立 → **38 小时 380+ 次失败，重试一次都没跑过**。
（DEBUG 日志显示两轮 5 端点都请求了，但分类完全相同，属于重复劳动。）

### 缺陷 3：session_state 传感器停更

**机制（HA 2026.10.4 源码 `helpers/update_coordinator.py` 确认）**：
`async_update_listeners()` **只在成功路径末尾被调用**。协调器抛 `UpdateFailed` 时，
listener 完全不会被通知，实体状态不会重写。这是 HA 的既定行为。

**完整因果链**：
1. HA 于 11-05 10:53 重启（`.ha_run.lock` mtime 佐证）
2. 重启后首次失败 → `fail_streak` 0→1、`last_error.at=10:53:44` → 抛 `UpdateFailed`
3. setup 走降级路径 → 实体注册 → 首次 `async_write_ha_state()`
   此刻 `fail_streak=1 < 5`、`auth_fail_streak=0` → `session_state` 算出 **"healthy"**
4. 之后每轮失败都走 `raise UpdateFailed` → listener 不通知 → **sensor 再也不重写**

实测吻合：sensor 属性 `fail_streak=1` / `last_error.at=2026-11-05 10:53:44`，
而协调器实际 `fail_streak=75`。HA 于 11-07 01:05 再次重启后，
sensor 的 `last_error.at` 立刻刷新为 `2026-11-07 01:05:33` —— **完全验证该机制**。

**附带问题：熔断兜底失效**
```python
CIRCUIT_COOLDOWN = 900.0   # 15 分钟
轮询间隔 = 1800 + jitter   # 30 分钟
```
熔断分支要求 `time.time() - self._last_fail_at < 900`，而 `_last_fail_at` 每轮失败都刷新
→ 该分支**永远进不去**（`return degraded` 才会通知 listener，兜底意图完全落空）。

**附带问题：network 类失败无退避**
`_apply_adaptive_interval` 只在认证失败时调用。
实测三个账号 `update_interval_seconds` 均为 1822/1834/1827 秒（基准区间 1800-1859），
移动 fail_streak=75 仍是基准 → 38 小时打了 380+ 次必然失败的请求。

### 缺陷 4：诊断包 `recent_events` 未按账号过滤

`diagnostics.py::_summarize_events` 读事件日志尾部 200 行后直接统计，
未按 carrier/phone 过滤 → 移动与联通账号下载到的诊断包 `recent_events` **完全相同**。

| 时间 | 事件 |
|---|---|
| 11-02 02:50~03:10 | 移动连续 4 次成功（16 字段） |
| 11-02 03:12 | v1.10.1 部署完成 |

间隔 31 分钟，恰为一次轮询周期。

## 五、遗留风险

1. **端点路径随运营商升级变更**：`serviceMargin/getMainPlan` 在维护期间返回 404。
   维护结束后它是否仍存在，需届时复核；若运营商改了路径，集成恢复后仍拿不到数据。
   建议后续加「连续 N 轮全公告 → 自动降级为维护态并通知用户」的行为（P1）。
2. **联通 cookie 需人工重登**：服务端会话过期，集成无 openid/短信自助通道。
3. **HA recorder DB 4.5 GB**：膨胀主因是 `miwifi_router` 集成（每设备 10 万条 states，
   共 670 万行），与本集成无关；`purge_keep_days: 5` 已生效但 SQLite 删除行不返还空间，
   需 VACUUM 或压缩备份。属独立支线。

## 六、运维探针

`mobile_health_probe.py`（本工作区）用于快速判定移动网厅状态：

```
方法   状态     判定            标题                    端点
GET   500     maintenance    升级公告                   spa/main/newHome
GET   404     maintenance    升级公告                   serviceMargin/getMainPlan
GET   404     maintenance    升级公告                   fareBalance
POST  500     maintenance    升级公告                   uniApi/getNewMarginInfo
GET   404     maintenance    升级公告                   score/news
POST  500     maintenance    升级公告                   uniApi/getMarginQueryInfo

结论: 运营商维护中：整站返回「升级公告」。凭据有效，集成侧应识别为 maintenance 并退避，无需重登。
```

判别规则：公告特征词 → `maintenance`；401/403 或登录特征 → `auth_expired`；
全端点 404 且非公告页 → 端点下线；200 → 正常。
