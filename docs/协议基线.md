# 协议基线报告（Protocol Baseline）

> 本报告记录 cn-carrier_monitor 所依赖的全部协议常量的**来源**与**实证状态**。
> 原则：任何常量必须可追溯到「官方 App 抓包」或「社区已验证实现」，并在
> 真实环境复验过。协议漂移的处置入口是 tests/ 契约套件与本表。

## 2. 本会话观察到的协议漂移症状（→ 对应防御）

| 症状 | 防御 |
|---|---|
| 移动 sendRandomCodeAction 拒绝服务端代发（"6"） | config_flow 不阻断，进入用户侧取码指引 |
| 电信 v1/v2 双接口族并存且密钥体系不同 | 双端点并存 + host 回退列表（`TELECOM_LOGIN_V2_HOSTS`） |
| HAOS coredns 对 189.cn 域名间歇解析失败（DNS server does not implement） | `net.py` AF_INET + 公共 DNS(223.5.5.5/119.29.29.29) |
| 响应结构随省份/套餐变化（湖南 600203 实测） | fixtures 固化已验证结构 + ruff F821 + 契约测试报警 |

## 3. 复验方法（任何人可重复）

1. `python -m pytest tests/ -q` — 全部契约（fixtures 即真实响应结构）
2. `python -m ruff check custom_components/ tests/` — 未定义名/死代码门禁
3. 真机链路：参照 README「各运营商接入指南」，短信链路每一步的成败都会在
   `custom_components.cn_carrier_monitor` 日志留下服务端原文
